# LEX-2026.0.3.1: Simplified pathName and Element Type Identification

## Overview

This document describes two simplifications in LEX-2026.0.3.1:

1. **Simplified Catalog Object Identifiers** - Using `pathName` instead of `locallyQualifiedObjectName`/`globallyQualifiedObjectName`
2. **Element Type Identification Patterns** - Three ways to identify node and edge types

## 1. Simplified pathName Syntax

### Change Summary

**Before (LEX-2026.0.3):**
```yaml
identifier:
  locallyQualifiedObjectName: "/benchmarks/ldbc/snb"
```

or

```yaml
identifier:
  globallyQualifiedObjectName: "https://ldbcouncil.org/schemas/|/benchmarks/ldbc/snb"
```

**After (LEX-2026.0.3.1):**
```yaml
pathName: "/benchmarks/ldbc/snb"
```

or

```yaml
pathName: "https://ldbcouncil.org/schemas/|/benchmarks/ldbc/snb"
```

### Rationale

- **Simpler syntax**: Single key `pathName` instead of two different keys
- **Same semantics**: The value format remains unchanged (LQON or GQON)
- **Less verbose**: Removes unnecessary `identifier:` wrapper

### Path Name Formats

#### Locally Qualified Object Name (LQON)
Starts with `/`:
```yaml
pathName: "/benchmarks/ldbc/snb"
pathName: "/examples/my-graph"
pathName: "/schemas/social-network"
```

#### Globally Qualified Object Name (GQON)
Contains IRI followed by `|` and LQON:
```yaml
pathName: "https://ldbcouncil.org/schemas/|/benchmarks/ldbc/snb"
pathName: "http://example.org/graphs/|/production/user-data"
```

### Examples

**Graph Schema:**
```yaml
pathName: /benchmarks/ldbc/snb
graphType:
  nodeTypes: [...]
  edgeTypes: [...]
```

**Graph Instance:**
```yaml
graph:
  pathName: "/examples/my-graph-instance"
  graphSchema:
    pathName: "/benchmarks/ldbc/snb"
    import: "snb-schema.yaml"
  storageSchema: {...}
```

**Catalog:**
```yaml
catalog:
  IRI: "https://example.org/catalog"
  graphSchemas:
    - name: "snb"
      qualifiedName: "/benchmarks/ldbc/snb"
      file: "$ref(snb-schema.yaml)"
```

## 2. Element Type Identification Patterns

### Three Identification Methods

LEX-2026.0.3.1 supports three ways to identify node and edge types:

1. **Single Label** (`typeLabel`) - Most common
2. **Multiple Labels** (`typeLabels`) - For types identified by label sets
3. **Anonymous with Index** (`index`) - For anonymous node types only

### Pattern 1: Single Label (typeLabel)

**Most common pattern** - Type identified by a single label:

```yaml
nodeType:
  typeLabel: Person
  implies:
    propertyTypes: [...]
```

```yaml
edgeType:
  typeLabel: KNOWS
  implies:
    propertyTypes: [...]
  direction: UNDIRECTED
  firstEndpointNodeType:
    typeLabel: Person
  secondEndpointNodeType:
    typeLabel: Person
```

### Pattern 2: Multiple Labels (typeLabels)

**For types identified by multiple labels** - Useful for subtype relationships:

```yaml
nodeType:
  typeLabels: ["Post", "Message"]
  implies:
    supertypes: [Message]
    propertyTypes: [...]
```

```yaml
nodeType:
  typeLabels: ["Comment", "Message"]
  implies:
    supertypes: [Message]
    propertyTypes: [...]
```

**Referencing multi-label types in edges:**
```yaml
edgeType:
  typeLabel: LIKES
  implies:
    propertyTypes: [...]
  direction: DIRECTED
  firstEndpointNodeType:
    typeLabel: Person
  secondEndpointNodeType:
    typeLabels: ["Post", "Message"]  # References Post by its labels
```

### Pattern 3: Anonymous with Index (index)

**For anonymous node types** - Assigned monotonically increasing indices in lexical order:

```yaml
nodeTypes:
  # Anonymous node type with index 0
  - nodeType:
      index: 0
      implies:
        propertyTypes:
          - name: id
            valueType: INTEGER
            notNull: true
          - name: name
            valueType: STRING
  
  # Anonymous node type with index 1
  - nodeType:
      index: 1
      implies:
        propertyTypes:
          - name: id
            valueType: INTEGER
            notNull: true
          - name: title
            valueType: STRING
```

**Referencing anonymous indexed types in edges:**
```yaml
edgeType:
  typeLabel: WORKS_AT
  implies:
    propertyTypes: [...]
  direction: DIRECTED
  firstEndpointNodeType:
    typeLabel: Person
  secondEndpointNodeType:
    index: 0  # References anonymous node type with index 0
```

### Pattern 4: Anonymous Edge Types (No Identifier)

**Edge types can be anonymous** - No index assigned:

```yaml
edgeType:
  # No typeLabel, typeLabels, or index
  implies:
    propertyTypes:
      - name: weight
        valueType: FLOAT
  direction: DIRECTED
  firstEndpointNodeType:
    typeLabel: Person
  secondEndpointNodeType:
    typeLabel: Company
```

### Rules and Constraints

1. **Node Type Identification:**
   - Must use exactly one of: `typeLabel`, `typeLabels`, or `index`
   - Anonymous node types (with `index`) can only be referenced in edge endpoint specifications
   - Indices start at 0 and increase monotonically in lexical order

2. **Edge Type Identification:**
   - Can use `typeLabel`, `typeLabels`, or be anonymous (no identifier)
   - Anonymous edge types do NOT have indices
   - Edge types can reference node types by any identification method

3. **Endpoint References:**
   - Can reference node types using `typeLabel`, `typeLabels`, or `index`
   - Must match the identification method used in the node type definition

### Complete Example

See `src/grasch/examples/snb-special-identification-example.yaml` for a comprehensive example showing all patterns:

```yaml
pathName: /benchmarks/ldbc/snb-special

graphType:
  nodeTypes:
    # Pattern 1: Single label
    - nodeType:
        typeLabel: Person
        implies: {...}
    
    # Pattern 3: Anonymous with index
    - nodeType:
        index: 0
        implies: {...}
    
    - nodeType:
        index: 1
        implies: {...}
    
    # Pattern 1: Single label (base type)
    - nodeType:
        typeLabel: Message
        implies: {...}
    
    # Pattern 2: Multiple labels (subtype)
    - nodeType:
        typeLabels: ["Post", "Message"]
        implies:
          supertypes: [Message]
          propertyTypes: {...}
    
    # Pattern 2: Multiple labels (subtype)
    - nodeType:
        typeLabels: ["Comment", "Message"]
        implies:
          supertypes: [Message]
          propertyTypes: {...}
  
  edgeTypes:
    # Pattern 1: Named edge with single label
    - edgeType:
        typeLabel: KNOWS
        implies: {...}
        direction: UNDIRECTED
        firstEndpointNodeType:
          typeLabel: Person
        secondEndpointNodeType:
          typeLabel: Person
    
    # Edge referencing anonymous indexed node
    - edgeType:
        typeLabel: WORKS_AT
        implies: {...}
        direction: DIRECTED
        firstEndpointNodeType:
          typeLabel: Person
        secondEndpointNodeType:
          index: 0
    
    # Edge referencing multi-label node
    - edgeType:
        typeLabel: LIKES
        implies: {...}
        direction: DIRECTED
        firstEndpointNodeType:
          typeLabel: Person
        secondEndpointNodeType:
          typeLabels: ["Post", "Message"]
    
    # Pattern 4: Anonymous edge (no identifier)
    - edgeType:
        implies: {...}
        direction: DIRECTED
        firstEndpointNodeType:
          typeLabel: Person
        secondEndpointNodeType:
          typeLabels: ["Comment", "Message"]
```

## Migration Guide

### From LEX-2026.0.3 to LEX-2026.0.3.1

**Step 1: Update Identifiers**

Replace:
```yaml
identifier:
  locallyQualifiedObjectName: "/path"
```

With:
```yaml
pathName: "/path"
```

Replace:
```yaml
identifier:
  globallyQualifiedObjectName: "iri|/path"
```

With:
```yaml
pathName: "iri|/path"
```

**Step 2: Review Element Type Identification**

Most schemas using `typeLabel` require no changes. Consider using:
- `typeLabels` for types identified by multiple labels
- `index` for anonymous node types that need to be referenced
- No identifier for anonymous edge types

## Version History

- **LEX-2026.0.3.1**: Introduced simplified `pathName` syntax and formalized element type identification patterns (typeLabel, typeLabels, index, anonymous)
- **LEX-2026.0.3**: Used `identifier:` wrapper with `locallyQualifiedObjectName` and `globallyQualifiedObjectName`
