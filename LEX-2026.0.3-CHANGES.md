# LEX:2026.0.3 Changes from 0.2

## Document Version
- **Specification**: LEX-100r3 (12 November 2025)
- **Schema Version**: LEX:2026.0.3.1
- **Previous Version**: LEX:2026.0.2.1 (based on LEX-100r2)

## Summary
LEX:2026.0.3 implements changes from LEX-100r3, focusing on mandatory type labels, simplified type identification, import/modularization support, and subtyping capabilities.

## Breaking Changes

### 1. Mandatory Type Labels
**Impact**: HIGH - Affects all schema definitions

- **Change**: Type labels are now mandatory for all node and edge types
- **Before (0.2)**: `nodeTypeMinimumLabels: 0` (labels optional)
- **After (0.3)**: `nodeTypeMinimumLabels: 1` (at least one label required)
- **Rationale**: Aligns with GQL:2027 and simplifies type identification
- **Migration**: All node and edge types must have at least one label

### 2. Type Identification Simplification
**Impact**: MEDIUM - Affects type identifier structure

- **Change**: Focus on type name labels as primary identification method
- **Supported Methods**:
  1. `typeNameLabel`: Single label serving as type name (preferred)
  2. `typeIdentifyingLabels`: Set of labels for complex identification
  3. Type index: Integer index for anonymous types
- **Rationale**: Simplifies common case while supporting advanced scenarios

## New Features

### 3. File References in Catalogs
**Impact**: LOW - Optional feature

- **Feature**: Catalog entries can reference external files
- **Syntax**: `file: $ref('path/to/schema.yaml')`
- **Purpose**: Separates IRI from actual file location
- **Use Case**: IRI may be non-dereferenceable; file path provides actual location

**Example**:
```yaml
catalog:
  IRI: "https://ldbcouncil.org/schemas/"
  directories:
    - name: "benchmarks"
      graphSchemas:
        - name: "snb"
          file: $ref('schemas/snb-schema.yaml')
```

### 4. Import/Modularization Support
**Impact**: MEDIUM - Enables schema composition

- **Feature**: Schemas can import external modules using `$ref`
- **Syntax**: Swagger-style `$ref('<file path>')`
- **Applies To**:
  - Graph types
  - Node types
  - Edge types
  - Property types
- **Benefit**: Enables distributed/partitioned schemas

**Example**:
```yaml
graphType:
  nodeTypes:
    $ref: 'common-node-types.yaml'
  edgeTypes:
    - edgeTypeIdentifier:
        typeNameLabel: "KNOWS"
      # ... rest of definition
```

### 5. Subtyping Support
**Impact**: MEDIUM - Enables type hierarchies

- **Feature**: Node types can declare supertypes
- **Syntax**: `supertypes: [TypeLabel1, TypeLabel2]`
- **Behavior**: Pulls in labels and property types from supertypes
- **Style**: Java interface mixin pattern

**Example**:
```yaml
nodeTypes:
  - nodeTypeIdentifier:
      typeNameLabel: "Employee"
    labels: ["Employee"]
    supertypes: ["Person", "Worker"]
    propertyTypes:
      - name: "employeeId"
        valueType:
          name: "INTEGER"
```

### 6. Type Interpretation Modes
**Impact**: MEDIUM - Affects validation behavior

- **Feature**: Control how types are interpreted during validation
- **Values**:
  - `exactlyOfThisType` (default): Exact match required
  - `anySubtypeOf`: Covariant interpretation (at least these attributes)
  - `anyProperSubtypeOf`: Proper subtype required
- **Default**: `exactlyOfThisType` (maintains backward compatibility)

**Example**:
```yaml
graphType:
  typeInterpretation: "anySubtypeOf"
  nodeTypes:
    - nodeTypeIdentifier:
        typeNameLabel: "Person"
      # ... definition
```

### 7. Extension Interpretation
**Impact**: MEDIUM - Controls extensibility

- **Feature**: Control whether types can be extended
- **Values**:
  - `open: true` / `closed: false`: Allow undefined subtypes
  - `open: false` / `closed: true`: Only defined subtypes allowed (default)
- **Applies To**: Labels and property types separately
- **Default**: `closed: true` (GQL:2027 setting)

**Example**:
```yaml
nodeTypes:
  - nodeTypeIdentifier:
      typeNameLabel: "Person"
    labels: ["Person"]
    extensionInterpretation:
      open: true
    propertyTypes:
      # ... properties
      extensionInterpretation:
        closed: true
```

### 8. Qualified Names in Catalogs
**Impact**: LOW - Additional metadata

- **Feature**: Catalog entries include computed qualified names
- **Types**:
  - GQON (Globally Qualified Object Name): When catalog has IRI
  - LQON (Locally Qualified Object Name): When no IRI
- **Format**: 
  - GQON: `https://example.com|/path/to/object`
  - LQON: `/path/to/object`
- **Purpose**: Explicit identification of catalog objects

## JSON Schema Changes

### Required Updates

1. **Node/Edge Type Identifiers**
   - Update minimum labels from 0 to 1
   - Maintain support for three identification methods

2. **New Optional Fields**
   - `supertypes`: Array of type label strings
   - `typeInterpretation`: Enum (exactlyOfThisType, anySubtypeOf, anyProperSubtypeOf)
   - `extensionInterpretation`: Object with `open` or `closed` boolean
   - `file`: String with $ref pattern

3. **Catalog Enhancements**
   - Add `qualifiedName` to directory, graph, and graphSchema objects
   - Add optional `file` reference field

4. **Import Support**
   - Allow `$ref` in appropriate locations
   - Document $ref resolution behavior

## Migration Guide

### From 0.2.1 to 0.3.1

#### Step 1: Ensure All Types Have Labels
```yaml
# Before (0.2.1) - This was valid
nodeTypes:
  - nodeTypeIdentifier:
      nodeTypeIndex: 0
    labels: []  # Empty labels allowed
    propertyTypes: [...]

# After (0.3.1) - Must have at least one label
nodeTypes:
  - nodeTypeIdentifier:
      typeNameLabel: "UnnamedType"  # Or appropriate name
    labels: ["UnnamedType"]
    propertyTypes: [...]
```

#### Step 2: Update Minimum Label Constraints
```yaml
# Before (0.2.1)
graphType:
  nodeTypeMinimumLabels: 0
  edgeTypeMinimumLabels: 0

# After (0.3.1)
graphType:
  nodeTypeMinimumLabels: 1  # Now required
  edgeTypeMinimumLabels: 1  # Now required
```

#### Step 3: (Optional) Add Subtyping
```yaml
# New in 0.3.1 - Optional feature
nodeTypes:
  - nodeTypeIdentifier:
      typeNameLabel: "Employee"
    labels: ["Employee"]
    supertypes: ["Person"]  # Inherits from Person
    propertyTypes: [...]
```

#### Step 4: (Optional) Use Imports
```yaml
# New in 0.3.1 - Optional feature
graphType:
  nodeTypes:
    $ref: 'common-types.yaml'
```

## Backward Compatibility

### Compatible Changes
- File references (optional)
- Import support (optional)
- Subtyping (optional)
- Type interpretation (defaults to 0.2 behavior)
- Extension interpretation (defaults to 0.2 behavior)

### Incompatible Changes
- **Mandatory labels**: Schemas with label-less types will fail validation
- **Minimum label constraints**: Default changed from 0 to 1

### Compatibility Strategy
- 0.2.1 schemas with labels will validate against 0.3.1 schema
- 0.2.1 schemas without labels will need migration
- New 0.3.1 features are optional and backward compatible
