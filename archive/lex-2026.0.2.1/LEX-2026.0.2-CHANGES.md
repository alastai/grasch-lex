# LEX:2026.0.2 Changes Summary

## Overview

LEX:2026.0.2 implements the LEX-100r2 specification, introducing significant enhancements to the catalog structure, type identification system, and value type handling.

## Key Changes from LEX:2026.0.1

### 1. Enhanced Catalog Structure

#### LQON/GQON Support
- **Before (0.1)**: Complex nested identifier structure with `root`, `directory`, `name`
- **After (0.2)**: Simplified LQON/GQON format
  - **LQON**: `locallyQualifiedObjectName: "/benchmarks/ldbc/snb"`
  - **GQON**: `globallyQualifiedObjectName: "https://ldbcouncil.org/schemas/|/benchmarks/ldbc/finbench"`

#### Benefits
- Cleaner, more intuitive addressing
- Global identification with IRI support
- Pipe-delimited syntax for IRI|path separation

### 2. Flexible Type Identification System

#### Node Type Identification
- **Before (0.1)**: Only integer `index` supported
- **After (0.2)**: Three flexible options:
  ```yaml
  nodeTypeIdentifier:
    typeNameLabel: "Person"           # Single label identification
    # OR
    typeIdentifyingLabels: ["Person"] # Multi-label identification  
    # OR
    nodeTypeIndex: 0                  # Index fallback
  ```

#### Edge Type Identification
- **Before (0.1)**: No explicit edge type identification
- **After (0.2)**: Same flexible system as node types:
  ```yaml
  edgeTypeIdentifier:
    typeNameLabel: "KNOWS"            # Single label identification
    # OR
    typeIdentifyingLabels: ["KNOWS"]  # Multi-label identification
    # OR  
    edgeTypeIndex: 0                  # Index fallback
  ```

### 3. Enhanced Endpoint References

#### Flexible Endpoint Identification
- **Before (0.1)**: Edge endpoints referenced by integer indices only
- **After (0.2)**: Edge endpoints can reference node types by any identifier method:
  ```yaml
  firstEndpointNodeTypeIdentifier:
    typeNameLabel: "Person"
  secondEndpointNodeTypeIdentifier:
    typeIdentifyingLabels: ["Post", "Comment"]  # Multi-type endpoints
  ```

### 4. Value Type System Updates

#### Parameter Naming
- **Before (0.1)**: `NULLABLE: false` (uppercase)
- **After (0.2)**: `nullable: false` (lowercase)

#### Default VTS
- **Before (0.1)**: VTS must be explicitly specified
- **After (0.2)**: CANONICAL VTS is default when omitted

#### Version Updates
- **Before (0.1)**: Canonical VTS version "2025.1"
- **After (0.2)**: Canonical VTS version "2025.0"

## Example Comparisons

### Identifier Structure

**LEX:2026.0.1**:
```yaml
identifier:
  name: "ldbc-snb"
  directory: ["benchmarks", "ldbc"]
  root: "https://ldbcouncil.org/schemas/"
```

**LEX:2026.0.2**:
```yaml
identifier:
  locallyQualifiedObjectName: "/benchmarks/ldbc/snb"
  # OR for global addressing:
  # globallyQualifiedObjectName: "https://ldbcouncil.org/schemas/|/benchmarks/ldbc/snb"
```

### Node Type Definition

**LEX:2026.0.1**:
```yaml
nodeTypes:
  - index: 0
    labels: ["Person"]
    propertyTypes:
      - name: "id"
        valueType:
          name: "INTEGER"
          parameters:
            NULLABLE: false
```

**LEX:2026.0.2**:
```yaml
nodeTypes:
  - nodeTypeIdentifier:
      typeNameLabel: "Person"
    labels: ["Person"]
    propertyTypes:
      - name: "id"
        valueType:
          name: "INTEGER"
          parameters:
            nullable: false
```

### Edge Type Definition

**LEX:2026.0.1**:
```yaml
edgeTypes:
  - labels: ["KNOWS"]
    direction: "UNDIRECTED"
    firstEndpointNodeType: 0      # Integer index only
    secondEndpointNodeType: 0     # Integer index only
```

**LEX:2026.0.2**:
```yaml
edgeTypes:
  - edgeTypeIdentifier:
      typeNameLabel: "KNOWS"
    labels: ["KNOWS"]
    direction: "UNDIRECTED"
    firstEndpointNodeTypeIdentifier:
      typeNameLabel: "Person"     # Flexible identification
    secondEndpointNodeTypeIdentifier:
      typeNameLabel: "Person"     # Flexible identification
```

## Migration Guide

### From 0.1 to 0.2

1. **Update Identifiers**:
   - Replace nested identifier structure with LQON/GQON format
   - Choose LQON for local addressing or GQON for global addressing

2. **Add Type Identifiers**:
   - Add `nodeTypeIdentifier` to all node types
   - Add `edgeTypeIdentifier` to all edge types
   - Use `typeNameLabel` for simple cases, `typeIdentifyingLabels` for complex cases

3. **Update Endpoint References**:
   - Replace integer endpoint references with flexible identifiers
   - Use same identifier format as used in type definitions

4. **Update Value Type Parameters**:
   - Change `NULLABLE` to `nullable` (lowercase)
   - Remove explicit `valueTypeSystemName: "CANONICAL"` (now default)

5. **Validate**:
   - Use new validation scripts: `validate_snb_lex_0_2_schema.py`, `validate_finbench_lex_0_2_schema.py`

## Benefits of 0.2

1. **Improved Usability**: Label-based identification is more intuitive than numeric indices
2. **Enhanced Flexibility**: Multiple identification methods support different use cases
3. **Better Addressing**: LQON/GQON provides cleaner, more standard addressing
4. **Global Identification**: GQON enables globally unique schema identification
5. **Simplified Defaults**: CANONICAL VTS default reduces boilerplate
6. **Standards Alignment**: Follows LEX-100r2 specification more closely

## Backward Compatibility

LEX:2026.0.2 is **not backward compatible** with 0.1 due to structural changes in:
- Identifier format
- Type identification system  
- Endpoint reference format
- Parameter naming conventions

Both versions are maintained separately to preserve version history and enable gradual migration.

## File Naming Updates

### JSON Schema File
- **File Name**: `lex-2026.0.2.schema.json` (simplified from `lex-2026.0.2-graph-schema.schema.json`)
- **Scope**: Expanded to support all three specification types:
  - Graph catalogs
  - Graph schemas  
  - Graph instances
- **Description**: "JSON Schema for specifications of graph catalogs, graph schemas and graph instances, allowing YAML spec documents for all three classes of specification"
