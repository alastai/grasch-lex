# LEX-2026.0.3.1: Type Interpretation Descriptors

## Overview

This document describes two type interpretation descriptor mechanisms in LEX-2026.0.3.1:

1. **Graph Schema Type Interpretation** - Controls how a graph instance interprets its schema types
2. **Element Type Interpretation** - Controls which element types are included in a schema and how they match

**Key Principle**: Interpretation descriptors wrap (are placed above/outside) the elements they govern.

## 1. Graph Schema Type Interpretation

### Purpose
Allows a graph instance to specify how strictly it conforms to its schema's type definitions.

### Location
Within a `graph` descriptor, wrapping the `graphSchema` descriptor.

### Syntax
```yaml
graph:
  identifier: {...}
  
  <interpretation-mode>:
    graphSchema:
      identifier: {...}
      import: "..."
  
  storageSchema: {...}
```

### Interpretation Modes

#### Default: `exactlyOfThisSchemaType`
- **Strictest mode** (default when omitted)
- Graph data must match schema types exactly
- No subtypes allowed
- Use case: Strict validation, data quality enforcement

```yaml
# Default - no interpretation descriptor needed
graph:
  identifier: {...}
  graphSchema:
    identifier: {...}
    import: "..."
```

Or explicitly:
```yaml
graph:
  identifier: {...}
  exactlyOfThisSchemaType:
    graphSchema:
      identifier: {...}
      import: "..."
```

#### `subtypesOfSchemaType`
- **Flexible mode**
- Graph data can be of the schema type OR any subtype
- Includes exact type matches
- Use case: Extensible schemas, polymorphic data

```yaml
graph:
  identifier: {...}
  subtypesOfSchemaType:
    graphSchema:
      identifier: {...}
      import: "..."
```

#### `properSubtypesOfSchemaType`
- **Subtype-only mode**
- Graph data must be a proper subtype (excludes exact type)
- Use case: Abstract base types that should never be instantiated directly

```yaml
graph:
  identifier: {...}
  properSubtypesOfSchemaType:
    graphSchema:
      identifier: {...}
      import: "..."
```

### Complete Examples

**Example 1: Default exact matching (omitted)**
```yaml
graph:
  identifier:
    locallyQualifiedObjectName: "/examples/strict-graph"
  
  graphSchema:
    identifier:
      locallyQualifiedObjectName: "/schemas/social-network"
    import: "social-network-schema.yaml"
  
  storageSchema:
    storageType: "kuzu"
    databasePath: "./data/strict-graph.kuzu"
```

**Example 2: Allow subtypes**
```yaml
graph:
  identifier:
    locallyQualifiedObjectName: "/examples/flexible-graph"
  
  subtypesOfSchemaType:
    graphSchema:
      identifier:
        locallyQualifiedObjectName: "/schemas/social-network"
      import: "social-network-schema.yaml"
  
  storageSchema:
    storageType: "kuzu"
    databasePath: "./data/flexible-graph.kuzu"
```

**Example 3: Only proper subtypes**
```yaml
graph:
  identifier:
    locallyQualifiedObjectName: "/examples/abstract-graph"
  
  properSubtypesOfSchemaType:
    graphSchema:
      identifier:
        locallyQualifiedObjectName: "/schemas/abstract-types"
      import: "abstract-types-schema.yaml"
  
  storageSchema:
    storageType: "kuzu"
    databasePath: "./data/abstract-graph.kuzu"
```

## 2. Element Type Interpretation

### Purpose
Specifies which element types (node types and edge types) are included in a schema and how they should be matched during validation.

### Location
Within a `graphType` descriptor, wrapping the `nodeTypes` and/or `edgeTypes` it governs.

### Syntax
```yaml
identifier: {...}
graphType:
  # Default elements (no interpretation descriptor)
  nodeTypes: [...]
  
  # Interpreted elements
  <interpretation-mode>:
    nodeTypes: [...]
    # and/or
    edgeTypes: [...]
```

### Interpretation Modes

#### Default: `exactlyOfTheseElementTypes`
- Elements must match specified types exactly (default when omitted)
- No subtypes allowed

#### `subtypesOfTheseElementTypes`
- Elements can be of specified types OR their subtypes
- Includes exact type matches

#### `properSubtypesOfTheseElementTypes`
- Elements must be proper subtypes (excludes exact types)
- Use case: Abstract base types

### Scope Patterns

#### Pattern 1: Default (No Descriptor)
All element types use exact matching:
```yaml
graphType:
  nodeTypes:
    - nodeType: {...}
  edgeTypes:
    - edgeType: {...}
```

#### Pattern 2: Single Interpretation Scope
Apply one interpretation to a group of types:
```yaml
graphType:
  # Some types with default exact matching
  nodeTypes:
    - nodeType:
        typeLabel: Person
        implies: {...}
  
  # Other types with subtype matching
  subtypesOfTheseElementTypes:
    nodeTypes:
      - nodeType:
          typeLabel: Message
          implies: {...}
      - nodeType:
          typeLabel: Post
          implies:
            supertypes: [Message]
            propertyTypes: {...}
```

#### Pattern 3: Multiple Interpretation Scopes
Different interpretations for different type groups:
```yaml
graphType:
  # Exact matching for some nodes
  nodeTypes:
    - nodeType:
        typeLabel: Person
        implies: {...}
  
  # Subtype matching for other nodes
  subtypesOfTheseElementTypes:
    nodeTypes:
      - nodeType:
          typeLabel: Company
          implies: {...}
  
  # Proper subtype matching for edges
  properSubtypesOfTheseElementTypes:
    edgeTypes:
      - edgeType:
          typeLabel: RELATIONSHIP
          implies: {...}
```

### Complete Examples

**Example 1: Default exact matching**
```yaml
identifier:
  locallyQualifiedObjectName: "/schemas/strict-schema"

graphType:
  $ref: graph_type_defaults.yaml
  
  nodeTypes:
    - nodeType:
        typeLabel: Person
        implies:
          propertyTypes:
            - name: id
              valueType: INTEGER
              notNull: true
  
  edgeTypes:
    - edgeType:
        typeLabel: KNOWS
        implies:
          propertyTypes: []
        direction: UNDIRECTED
        firstEndpointNodeType:
          typeLabel: Person
        secondEndpointNodeType:
          typeLabel: Person
```

**Example 2: Subtypes for message hierarchy**
```yaml
identifier:
  locallyQualifiedObjectName: "/schemas/message-hierarchy"

graphType:
  $ref: graph_type_defaults.yaml
  
  nodeTypes:
    - nodeType:
        typeLabel: Person
        implies:
          propertyTypes:
            - name: id
              valueType: INTEGER
              notNull: true
  
  # Message and its subtypes
  subtypesOfTheseElementTypes:
    nodeTypes:
      - nodeType:
          typeLabel: Message
          implies:
            propertyTypes:
              - name: id
                valueType: INTEGER
                notNull: true
              - name: content
                valueType: STRING
      
      - nodeType:
          typeLabel: Post
          implies:
            supertypes: [Message]
            propertyTypes:
              - name: imageFile
                valueType: STRING
      
      - nodeType:
          typeLabel: Comment
          implies:
            supertypes: [Message]
            propertyTypes:
              - name: replyCount
                valueType: INTEGER
  
  edgeTypes:
    - edgeType:
        typeLabel: CREATED
        implies:
          propertyTypes: []
        direction: DIRECTED
        firstEndpointNodeType:
          typeLabel: Person
        secondEndpointNodeType:
          typeLabel: Message  # Matches Message, Post, or Comment
```

**Example 3: Abstract base type (proper subtypes only)**
```yaml
identifier:
  locallyQualifiedObjectName: "/schemas/abstract-relationship"

graphType:
  $ref: graph_type_defaults.yaml
  
  nodeTypes:
    - nodeType:
        typeLabel: Person
        implies:
          propertyTypes:
            - name: id
              valueType: INTEGER
              notNull: true
  
  # RELATIONSHIP is abstract - only subtypes can be instantiated
  properSubtypesOfTheseElementTypes:
    edgeTypes:
      - edgeType:
          typeLabel: RELATIONSHIP  # Abstract base
          implies:
            propertyTypes:
              - name: since
                valueType: DATE
          direction: DIRECTED
          firstEndpointNodeType:
            typeLabel: Person
          secondEndpointNodeType:
            typeLabel: Person
      
      - edgeType:
          typeLabel: KNOWS  # Concrete subtype
          implies:
            supertypes: [RELATIONSHIP]
            propertyTypes:
              - name: strength
                valueType: FLOAT
          direction: UNDIRECTED
          firstEndpointNodeType:
            typeLabel: Person
          secondEndpointNodeType:
            typeLabel: Person
```

**Example 4: Mixed interpretations**
```yaml
identifier:
  locallyQualifiedObjectName: "/schemas/mixed-interpretation"

graphType:
  $ref: graph_type_defaults.yaml
  
  # Exact matching for Person (default)
  nodeTypes:
    - nodeType:
        typeLabel: Person
        implies:
          propertyTypes:
            - name: id
              valueType: INTEGER
              notNull: true
  
  # Subtypes allowed for Company hierarchy
  subtypesOfTheseElementTypes:
    nodeTypes:
      - nodeType:
          typeLabel: Company
          implies:
            propertyTypes:
              - name: id
                valueType: INTEGER
                notNull: true
      
      - nodeType:
          typeLabel: TechCompany
          implies:
            supertypes: [Company]
            propertyTypes:
              - name: techStack
                valueType: STRING
  
  # Exact matching for edges (default)
  edgeTypes:
    - edgeType:
        typeLabel: WORKS_FOR
        implies:
          propertyTypes:
            - name: startDate
              valueType: DATE
        direction: DIRECTED
        firstEndpointNodeType:
          typeLabel: Person
        secondEndpointNodeType:
          typeLabel: Company  # Matches Company or TechCompany
```

## Semantic Differences

### Graph Schema Type Interpretation vs Element Type Interpretation

| Aspect | Graph Schema Type Interpretation | Element Type Interpretation |
|--------|----------------------------------|----------------------------|
| **Level** | Graph instance | Graph schema |
| **Wraps** | graphSchema descriptor | nodeTypes/edgeTypes descriptors |
| **Scope** | How graph interprets entire schema | Which element types are included |
| **Purpose** | Runtime validation mode | Schema composition control |
| **Granularity** | Applies to all types in schema | Can apply to specific type groups |
| **Default** | exactlyOfThisSchemaType | exactlyOfTheseElementTypes |

### When to Use Each

**Use Graph Schema Type Interpretation when:**
- You want to control how strictly a graph instance validates against its schema
- You need different validation modes for different graph instances using the same schema
- You're implementing polymorphic data storage

**Use Element Type Interpretation when:**
- You're defining which types are part of a schema
- You want to create abstract base types
- You need fine-grained control over type matching per element category
- You're building modular, extensible schemas with type hierarchies

## Default Behavior

**Critical**: Both interpretation descriptors default to exact matching when omitted:

```yaml
# These are equivalent:
graph:
  identifier: {...}
  graphSchema: {...}

# and:
graph:
  identifier: {...}
  exactlyOfThisSchemaType:
    graphSchema: {...}
```

```yaml
# These are equivalent:
graphType:
  nodeTypes: [...]

# and:
graphType:
  exactlyOfTheseElementTypes:
    nodeTypes: [...]
```

## Validation Rules

1. Only one interpretation mode can wrap a given descriptor
2. Element type interpretation can have multiple scopes with different modes
3. Type labels referenced must exist in the schema
4. Proper subtype interpretation requires at least one subtype to be defined
5. The interpretation descriptor must be at the same level as (sibling to) the descriptor it would wrap

## Interaction Between Descriptors

Both descriptors can be used together in a complete graph specification:

```yaml
# Graph instance with flexible schema interpretation
graph:
  identifier:
    locallyQualifiedObjectName: "/examples/flexible-graph"
  
  # Graph-level: Allow subtypes of schema types
  subtypesOfSchemaType:
    graphSchema:
      identifier:
        locallyQualifiedObjectName: "/schemas/extensible-social"
      
      # Schema definition with element type interpretation
      graphType:
        # Exact matching for Person nodes
        nodeTypes:
          - nodeType:
              typeLabel: Person
              implies: {...}
        
        # Subtypes allowed for Message hierarchy
        subtypesOfTheseElementTypes:
          nodeTypes:
            - nodeType:
                typeLabel: Message
                implies: {...}
            - nodeType:
                typeLabel: Post
                implies:
                  supertypes: [Message]
                  propertyTypes: {...}
        
        # Exact matching for edges
        edgeTypes:
          - edgeType:
              typeLabel: CREATED
              implies: {...}
  
  storageSchema: {...}
```
