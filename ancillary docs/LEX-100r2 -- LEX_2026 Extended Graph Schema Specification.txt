Introduction
Please see LEX-99 – GQL graph types, PCG graph views and LEX graph schemas for an explanation of the relationship of LEX to other schema languages. 


LEX:2026 is maintained, and versions of it are published by the Graph Data Council in close liaison with WG3 – the SQL and GQL standards committee – and other relevant projects, for example Apache GraphAr.


These projects share an interest in standard representations of identified property graphs, graph schemas and storage schemas, which are neutral with respect to data language, general-purpose programming language and value type system (VTS).


The concrete syntax of LEX is YAML, whose format and some restrictions can be defined in JSON Schema. The JSON Schemas for LEX are included in this specification, directly or by reference, and are versioned in lock-step with it.  


YAML documents are concrete representations of an abstract syntax defined here, which is a superset of the information content of a GQL:2027 catalog/graph type, and of a SQL:2023/PGQ tabular property graph. 


Specification status
This document (for short, the LEX-100 Specification) is a “rolling draft” document that is being built up section by section (through multiple revisions) to define LEX:2026 as a superset of GQL:2027.


At this stage LEX is an informal, de facto standard which is required by Apache GraphAr (in incubation), and GDC’s Text2GraphQuery project.[1] LEX does a useful job that is not currently within the remit of WG3. 


This also means that LEX can move faster and further than GQL, while recognizing the primary of the official International Standard. 


This specification uses major/minor versioning. A major version has a given functional scope, and its minor versions represent successive approximations of delivery of that scope. 


You can refer to a major version as LEX:2026.<major> and to a specific minor version as LEX:2026.<major>.<minor>. For example, the functionality of the first major version LEX:2026.0 is described in the table that follows.

LEX descriptors and abstract syntax
Concepts and components
A descriptor[2] specifies the abstract syntax of an object which is part of a hierarchically-organized collection of objects called a graph catalog. A descriptor defines a piece of information required by a language operation. 
In this version, we define the abstract syntax of 
1. A graph catalog’s collection, which defines a directory structure containing a collection of named primary catalog objects. A PCO is either a graph or a graph schema[3].
2. A system of value type systems, including a lowest common denominator or canonical VTS, with mappings of its value types to default value types in external VTS, like the datatypes of SQL or Cypher or Parquet/Arrow.
3. A single logical-model graph schema (structural graph type plus graph constraints) which is required for the operation of schema validation of a (data) graph instance. 
4. A set of physical-model graph storage schemas, which are required to support the operations of graph serialization and deserialization.
The goal of this version is to create a minimal capability which will replace the YAML used by GraphAr for logical schema with LEX YAML, and add optional physical storage schemas to LEX which are required by GraphAr. The final shape of this version of LEX YAML will therefore be agreed in conjunction with the GraphAr project. However, LEX logical schemas will always be usable independently of graph serialization. 
Potential added functionality in future versions is summarized in Appendix A: Possible future functionality.
Descriptor syntax
A descriptor has a name, which may be quoted in double quotation marks, and may have a value and/or contents. 
A prefix – indicates inclusion by the first preceding descriptor to be indented by less than this one. The prefix ? indicates that the descriptor is optional (0 or 1 instances) and the symbol | indicates a choice. The prefix + indicates repetition of 1 or more instances of the descriptor, and the suffix * indicates repetition of 0 or more instances. 
Free text is used to describe or define a descriptor’s contents or meaning. A parameter or parameters in angle brackets may be indicated. This value will either be given directly in CAPITALIZED text, or it will be represented by a type name like <string> or <integer> or <map K → V> etc. If symbols in italics like K and V are shown then they will be defined in accompanying free text. 
LEX Graph Catalog abstract syntax
A catalog is a collection of objects, each of which is the last node in a path from the root of a tree to one of its leafs. A path in a tree is a sequence of nodes, > 0 elements. 


If the catalog tree has depth 0 (i.e. it only contains a root node), then that root node is also a leaf node, and that node is an object. The path to that node is a single node. If the tree has depth 1 (has a root node, which has some children nodes) then each object\s path is root-leaf. If the tree has depth 2 (or more) then each object’s path is root-inner+-leaf (where inner+ represents a sequence of one or more inner nodes).
A tree-structured document can be used to represent the union of the paths which lead to an object in the collection, whose root element is called “catalog”. There may be inner nodes, which are children of the catalog or children of inner nodes, and these inner node elements are called “directory”. A directory may have a child which is a leaf node called either “graph” or “graphSchema”. 
The “catalog” has an optional child element called “IRI”, which if present has a string value which is a valid IRI. This IRI need not be referenceable. Each “directory”, “graph” or “graph Schema” element has a child called “name”, with a string value. 
A path from the root to an object can be identified by forming a locally-qualified object name (LQON), where the “catalog” root is represented by the string “/” (irrespective of the presence of an “IRI” element, or of its value). Each directory in the path is then represented by the value of its “name”, with the character “/” appended, and the “graph” or “graphSchema” object is represented by the value of its “name”.
An example of a LQON might be:
   /finance/eod/valuationSchema
If the “catalog” element has a child “IRI” then the path to an object can be identified by a globally-qualified object name (GQON). For a given object with a LQON, its GQON will be the LQON prefixed by the value of “IRI”, with a solidus appended. For example:
   https://finance.bank.com|/finance/eod/valuationSchema
Notice that the IRI is delimited from the LQON by a pipe symbol. 
In the abstract syntax for a graph or graph schema object given below the globally- or locally-qualified name element has a value which has the format of a GQON or LQON respectively. A LQON is a path name of exactly the form defined by GQL:2027. A GQON extends an LQON, adding a facility not present in GQL:2027, namely the identification of a catalog by an IRI. Note that 
If a graph is in a catalog which is globally identified by an IRI, then it follows that every identified object contained in that graph has a globally unique identifier. In principle this opens the road to giving IRIs to graph elements (nodes, edges) and to their properties, as implementations are responsible for allocating graph-unique identifiers to all of their graphs’ elements. 
It is up to an application or tool or implementation using this specification to ensure that objects which are enumerated in the catalog match up with the name elements of YAML documents for graphs and graph schemas. One way of doing this is to give a catalog an IRI which is referenceable, and to give a graph or schema document a globally-qualified name such that the GQON dereferences to the YAML document.

LEX Graph Schema abstract syntax
A LEX:2026 graph schema (graph schema, or schema for short) contains an identifier, a structural graph type (akin to a graph type as defined in GQL:2024, i.e. without constraints), and a set of graph constraints. 
To put it another way, a graph schema contains 
1. an identifier which is either 1) a path-qualified graph type name as defined in GQL:2027 (a LEX LQON), or 2) a LEX GQON, 
2. a graph type, like the one defined in GQL:2024 (or GQL:2027 but minus its set of constraints)
3. a (possibly empty) set of constraints, which could be exactly the set of constraints that can be present in a GQ::2027 graph type. That set has the same information contents that it would have had, if defined in GQL:2027. Note that in a LEX graph schema it is moved outside the graph type and is instead directly included by the graph schema. 
This organization seems logical because a constraint applies to a graph and not to a graph type. By separating constraints from the structural graph type, it becomes more natural to allow the definition of a set of constraints directly on a graph, even if that graph does not have a graph type. This is exactly the situation that obtains with Neo4j graphs.  
Types and constraints
A graph constraint is a rule that applies to a class of graphs, which narrows the possible values of each graph in the class. A graph type is a different kind of rule that has the same effect. A graph may not have a type, and it may have no constraints. Or it may have both. If it has both and a constraint can never be satisfied by virtue of the application of the type, then the constraint falls away – it is never applied, and it may as well have never been defined. 
For example, if a graph type specifies only two property types for a node type, and there is a key constraint which demands uniqueness of the compound value of three properties, only two of which are possibly present because of the limitation of the node type, then the key constraint will not operate for the collection of nodes of that node type. 
A constraint can be defined for a graph type, in which case the class of graphs to which it applies (its scope) is the set of graphs which conform to that graph type. Or, it can be defined directly for a single graph. The class of graphs is then the class of all graphs for which the constraint has been individually defined. 
The information content of a LEX:2026.0 graph schema is therefore intended to be a strict superset of the information content of a GQL:2027 graph type, even if organized differently.
Note that LEX:2026 may (over time, but not in its first major Version 0) define constraints which are not present in GQL:2027. Examples include cardinality constraints or value type facets or restrictions like max/min values, lengths, etc. 
It may also allow for user-defined types and for use of a de facto or proto-standard like JSON Schema or JSON Structure to define property types. None of the above additional features are supported by Version 0.
Catalog, schema, graph
A YAML document may specify a “catalog”, a “graph schema” or a “graph”. The abstract syntax of a specification object contains a parent or root which identifies the class of specification to which the object belongs. 
Graph schema: Identifier, owner and value type system
A graph schema specification object is classified and identified thus:


graph schema
    – identifier
        – locally-qualifed object name 
        | globally-qualified object name


A graph schema may be owned by a principal (i.e. a piece of authorization data which is meaningful to a system maintaining a catalog of graph schemas).
graph schema
    – identifier
    – ? principal <string>


Value type systems defines a set of value type systems, each of which is named, and consists of a set of named property value types, or just value types, for short. The names of these value types form a set. Each value type may also have parameters. 
Each graph schema includes a descriptor of its value type system, which is the type system’s name as given in this specification. If this is omitted then the canonical VTS (for some default version) is the default value.
graph schema
    – identifier
    – ? principal <string>
    – ? value type system name <string> // defaults to CANONICAL
Graph schema: structural graph type
A graph schema contains a graph type which describes the structure of conformant (schema-valid) data graphs or instances. 
graph schema
    – identifier
    – ? principal <string>
    – ? value type system name <string> // preferred names for types
    – graph type
A graph type descriptor contains the following descriptors:
    – graph type
        — graph preferred name // (implementation-defined (ID089) 
            GRAPH | PROPERTY GRAPH
        – node preferred name // (implementation-defined (ID090)
            NODE | VERTEX
        – edge preferred name // (implementation-defined (ID091)
            EDGE | RELATIONSHIP
        – node type minimum labels <positive integer> // (IL001)
        – node type maximum labels <positive integer> // (IL001)
        – node type minimum property types <positive integer> 
            // (IL002)
        – node type maximum property types <positive integer> 
            // (IL002)
        – edge type minimum labels <positive integer> // (IL001)
        – edge type maximum labels <positive integer> // (IL001)
        – edge type minimum property types // (IL002)
        – edge type maximum property types // (IL002)
        — node types <set>
        — edge types <set>


A set of node type descriptors looks like this
    – graph type
        — node types <set>
            – node type
            – node type
            . . .  


A node type descriptor contains the following descriptors
    – graph type
        — node types <set>
            – node type             
                – labels <set <string>>
                – property types <set>
                – nodeTypeIdentifier
A node type has a unique identifier which is one of:
1. an integer index, whose value indicates that the node type is the 0th, 1st, … etc. node type in the lexical order of the definition of the graph type
2. a type name label which is in the set of labels in the descriptor  – labels
3. a type identifying set of labels, which is a subset of the set of labels in the descriptor  – labels
The descriptor 
    – nodeTypeIdentifier 
is therefore equivalent to this choice:
    – nodeTypeIndex <integer> | 
      typeNameLabel <string starts alpha> | 
      typeIdentifyingLabels <set <string starts alpha>> 
Whatever the value of the node type identifier it must be unique for all node type identifiers. This means that the user can mix default node types with name labels with key label sets.  
A set of property type descriptors looks like this
    – graph type
        — node types <set>
            – node type
                – labels <set <string>>
                – property types <set>
                    – property type  
                        – name <string>
                        – value type
                    – property type  
                   . . . 


In a property types set, the names of any two property type members must not be equal. 
                                          
A value type descriptor contains an identifier, whose value is the name of a value type in the value type system of the containing LEX schema. The descriptor may include additional information indicated as parameters in the value type system’s table of value types.  
A value type descriptor looks like this
    – graph type
        — node types <set>
            – node type
                – labels <set <string>>
                – property types <set>
                    – property type  
                        – name <string>
                        – value type
                            – name <string>
                            – parameters <map <string> → <value>>


Where the value of the string key in the map of parameters will be the name of the parameter given in the value type system’s table of value types, and the value will be parameter dependent. So for example, any value type may contain the key nullable and the value TRUE, but other parameters like minimum or maximum length of a fixed length string may only make sense for particular value types. 


An edge type descriptor contains the following descriptors
    – graph type
        — edge types <set>
            – edge type
                – edge type identifier
                – labels <set <string>>
                – property types <set>
                – direction DIRECTED | UNDIRECTED
                – first endpoint node type identifier
                – second endpoint node type identifier | SAME 
                   
The descriptor 
    – edgeTypeIdentifier 
is therefore equivalent to this choice:
    – edgeTypeIndex <integer> | 
      typeNameLabel <string starts alpha> | 
      typeIdentifyingLabels <set <string starts alpha>> 
Whatever the value of the edge type identifier it must be unique for all node type identifiers. This means that the user can mix default node types with name labels with key label sets.  


The rules for the contents of the second and third descriptors contained in the edge type are identical to those for node types, with the difference that each reference to the set of node types or to a node type, isto be replaced with a reference to the set of edge types, or to an edge type, within the graph type. 


The next three descriptors contained by an edge type related to its orientation. An edge is either directed or undirected. If an edge type is directed then the first endpoint node type is the source of an edge of this type,  and the second is the destination of the edge. If the edge is undirected then the order of the endpoint node types is irrelevant (has no semantic). If the edge is a loop then the second endpoint node type descriptor has the meaning that it is the SAME as the first. 


Otherwise the value of each of the endpoint descriptors is a node type identifier for the endpoint concerned, which can be an index, a type name label, or a set of labels (a key label set) which identify the node type.  


Graph schema: Constraints
We have now dealt with the identifier and graph type of a graph schema. A graph schema can also have a descriptor for a set of constraints, which is possibly empty. 


graph schema
    – identifier
    – ? principal <string>
    – ? value type system name <string> // preferred names for types
    – graph type
    – ? constraints <map CK → C>
Where CK is a <string> which is a constraint name, and C is a constraint rule descriptor.   
A constraint descriptor has these contents:
    – constraints 
        – constraint
            – name <string>
            – rule
                – subject KEY | UNIQUE     
                – constraint pattern
                – unique key component property names <set>

LEX Graph abstract syntax
A graph (instance) descriptor may include any of a graph schema, a set of constraints and a storage schema.


Graph instance: without storage schema 
graph 
    – identifier
    – ? principal <string>
    – ? value type system name <string> 
    – ? graph schema <identifier>
    – ? constraints <map CK → C>
The content of these descriptors is the same as those for the graph schema descriptor, mutatis mutandis. If a graph’s graph schema contains a set of constraints then the graph cannot contain a second, independent set of constraints.


Graph instance: with storage schema
graph 
    – identifier
    – ? principal <string>
    – ? value type system name <string> 
    – ? graph schema <identifier>
    – ? constraints <map CK → C>
    – ? storage schema

LEX JSON Schema
LEX JSON Schema defines a concrete syntax for LEX, in the form of YAML. YAML documents can be produced which contain only the information defined in the abstract syntaxes for catalogs, schemas and graphs. The JSON Schema therefore defines permitted document for these three classes of specifications, and it also defines database value types, starting with the CANONICAL VTS, enabling YAML graph schema property types to be specified with a given canonical data or value type.
