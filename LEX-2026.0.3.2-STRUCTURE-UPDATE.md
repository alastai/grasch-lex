# LEX:2026.0.3.2 Structure Update

## Overview
This document describes the structural improvements made to LEX:2026.0.3.2 to simplify the schema format and better align with the LEX-100r3 specification.

## Changes Made

### 1. Renamed Type Identifiers
**Before:**
```yaml
nodeTypes:
  - nodeTypeIdentifier:
      typeLabel: "Person"
    implies:
      labels: ["Person"]
      propertyTypes: [...]

edgeTypes:
  - edgeTypeIdentifier:
      typeLabel: "KNOWS"
    implies:
      labels: ["KNOWS"]
      propertyTypes: [...]
    direction: "DIRECTED"
    firstEndpointNodeTypeIdentifier:
      typeLabel: "Person"
    secondEndpointNodeTypeIdentifier:
      typeLabel: "Person"
```

**After:**
```yaml
nodeTypes:
  - nodeType:
      typeLabel: "Person"
      implies:
        propertyTypes: [...]

edgeTypes:
  - edgeType:
      typeLabel: "KNOWS"
      implies:
        propertyTypes: [...]
      direction: "DIRECTED"
      firstEndpointNodeType:
        typeLabel: "Person"
      secondEndpointNodeType:
        typeLabel: "Person"
```

**Rationale:** Shorter, clearer names that better reflect the structure.

### 2. Moved `implies` to Same Level as `typeLabel`
**Before:**
```yaml
- nodeTypeIdentifier:
    typeLabel: "Person"
  implies:
    labels: ["Person"]
    propertyTypes: [...]
```

**After:**
```yaml
- nodeType:
    typeLabel: "Person"
    implies:
      propertyTypes: [...]
```

**Rationale:** The `implies` descriptor is part of the type definition, not a sibling to the identifier. This structure better reflects that `typeLabel` identifies the type, and `implies` describes what that type implies.

### 3. Omit `labels` When It Only Contains `typeLabel`
**Before:**
```yaml
- nodeType:
    typeLabel: "Person"
    implies:
      labels: ["Person"]  # Redundant!
      propertyTypes: [...]
```

**After:**
```yaml
- nodeType:
    typeLabel: "Person"
    implies:
      propertyTypes: [...]  # labels omitted - implied by typeLabel
```

**Rationale:** When a type has only one label that matches its `typeLabel`, the `labels` array is redundant. The LEX-100r3 spec marks `labels` as optional (`? labels`), allowing this simplification.

**When to include `labels`:**
- When the type has multiple labels
- When the labels differ from the `typeLabel`
- When using `typeIdentifyingLabels` instead of `typeLabel`

### 4. Moved Edge Endpoints and Direction Inside `edgeType`
**Before:**
```yaml
- edgeTypeIdentifier:
    typeLabel: "KNOWS"
  implies:
    propertyTypes: [...]
  direction: "DIRECTED"
  firstEndpointNodeTypeIdentifier:
    typeLabel: "Person"
  secondEndpointNodeTypeIdentifier:
    typeLabel: "Person"
```

**After:**
```yaml
- edgeType:
    typeLabel: "KNOWS"
    implies:
      propertyTypes: [...]
    direction: "DIRECTED"
    firstEndpointNodeType:
      typeLabel: "Person"
    secondEndpointNodeType:
      typeLabel: "Person"
```

**Rationale:** All edge type properties are now contained within the `edgeType` object, creating a cleaner structure.

### 5. Renamed Endpoint References
- `firstEndpointNodeTypeIdentifier` → `firstEndpointNodeType`
- `secondEndpointNodeTypeIdentifier` → `secondEndpointNodeType`

**Rationale:** Shorter names that are still clear and descriptive.

## Example: Complete Node Type

### Simple Node Type (labels omitted)
```yaml
- nodeType:
    typeLabel: "Person"
    implies:
      propertyTypes:
        - name: "id"
          valueType:
            name: "INTEGER"
            parameters:
              nullable: false
        - name: "name"
          valueType:
            name: "STRING"
            parameters:
              nullable: false
```

### Node Type with Supertypes
```yaml
- nodeType:
    typeLabel: "Employee"
    implies:
      supertypes: ["Person"]  # Inherits Person's properties
      propertyTypes:
        - name: "employeeId"
          valueType:
            name: "INTEGER"
            parameters:
              nullable: false
```

### Node Type with Multiple Labels
```yaml
- nodeType:
    typeLabel: "Manager"
    implies:
      labels: ["Manager", "Employee", "Person"]  # Multiple labels - must be explicit
      propertyTypes: [...]
```

## Migration Guide

### For Schema Authors
1. Rename `nodeTypeIdentifier` → `nodeType`
2. Rename `edgeTypeIdentifier` → `edgeType`
3. Move `implies` inside the type object (same level as `typeLabel`)
4. Remove `labels` array when it only contains the `typeLabel`
5. Rename endpoint references:
   - `firstEndpointNodeTypeIdentifier` → `firstEndpointNodeType`
   - `secondEndpointNodeTypeIdentifier` → `secondEndpointNodeType`

### For Tool Developers
Update code that accesses:
- `node_type['nodeTypeIdentifier']` → `node_type['nodeType']`
- `edge_type['edgeTypeIdentifier']` → `edge_type['edgeType']`
- `node_type['implies']` → `node_type['nodeType']['implies']`
- `edge_type['firstEndpointNodeTypeIdentifier']` → `edge_type['edgeType']['firstEndpointNodeType']`

## Benefits

1. **Cleaner Syntax**: Shorter, more intuitive names
2. **Less Redundancy**: No need to repeat the type label in the labels array
3. **Better Structure**: `implies` is clearly part of the type definition
4. **Spec Compliance**: Leverages the optional nature of `labels` in LEX-100r3
5. **Easier to Read**: Reduced nesting and clearer relationships

## Backward Compatibility

This is a **breaking change** from LEX:2026.0.3.0. Schemas using the old structure will need to be updated. However, the semantic meaning remains the same - this is purely a structural improvement.

## Version

This structure is effective as of **LEX:2026.0.3.2** (November 2024).
