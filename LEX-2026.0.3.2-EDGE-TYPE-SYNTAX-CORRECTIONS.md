# LEX-2026.0.3.2 Edge Type Syntax Corrections - Implementation Plan

## Summary of Corrections

This document outlines all corrections received regarding edge type syntax in LEX-2026.0.3.2 and the changes required to implement them across examples, tests, and schema.

## Corrections Received

### Correction 1: `and:` is NOT a Synonym
- `and:` is a distinct, required property for undirected edges
- It specifies the second endpoint
- It is NOT a synonym for `via:`, `arc:`, or `typeLabel:`

### Correction 2: Property Synonym Groups
Three distinct synonym groups with mutually exclusive members:

**Edge Label Properties:**
- Primary: `via:`
- Synonyms: `arc:`, `typeLabel:`

**Source Endpoint Properties:**
- Primary: `from:`
- Synonyms: `src:`, `source:`, `tail:`

**Destination Endpoint Properties:**
- Primary: `to:`
- Synonyms: `dst:`, `dest:`, `destination:`, `head:`

### Correction 3: Subtyping with `extends:` and `adding:`
Within both `directed:` and `undirected:` edge type definitions:
- `extends:` (optional) - Specifies parent type(s)
- `adding:` (optional) - Specifies additional properties/constraints
- `extends:` can appear without `adding:`
- `adding:` CANNOT appear without `extends:`
- Mutually exclusive with `implies:`

### Correction 4: Children of `adding:`
When `adding:` is present:
- `labels:` (optional)
- `propertyTypes:` (optional)

### Correction 5: Endpoint Node Type Specifications
Endpoint properties can specify node types in two ways:
1. **Type Reference**: Simple string (e.g., `Person`)
2. **Inline Node Type Definition**: Full definition starting with `nodeType:`

### Correction 6: Property Ordering Rules
**For Directed Edges:**
- Order: `from:` → `to:` → `via:` → `implies:` or `extends:`/`adding:` → `propertyTypes:`

**For Undirected Edges:**
- Order: `between:` → `and:` → `via:` → `implies:` or `extends:`/`adding:` → `propertyTypes:`

**Critical**: `via:` (or synonyms) must come AFTER endpoint specifications, and subtyping must come AFTER `via:`

## Required Changes

### 1. JSON Schema Updates (`src/grasch/schemas/lex-2026.0.3.2.schema.json`)

#### 1.1 Edge Label Property Definitions
**Current Issue**: May incorrectly treat `and:` as a synonym for edge labels

**Required Fix**:
- Ensure `via:`, `arc:`, `typeLabel:` are in one mutually exclusive group
- Ensure `and:` is a separate, required property for undirected edges
- Update schema to enforce mutual exclusivity within synonym groups

#### 1.2 Property Ordering Enforcement
**Current Issue**: Schema may not enforce correct property order

**Required Fix**:
- Use JSON Schema `propertyNames` and ordering constraints
- Enforce: endpoints → `via:` → subtyping → `propertyTypes:`
- Consider using `oneOf` patterns to enforce ordering

#### 1.3 Subtyping Options
**Current Issue**: May not properly handle `extends:`/`adding:` pattern

**Required Fix**:
- Add `extends:` property definition
- Add `adding:` property definition with children `labels:` and `propertyTypes:`
- Enforce dependency: `adding:` requires `extends:`
- Enforce mutual exclusivity: `implies:` XOR (`extends:` with optional `adding:`)

#### 1.4 Endpoint Specifications
**Current Issue**: May not support both type references and inline definitions

**Required Fix**:
- Allow endpoint properties to be either:
  - String (type reference)
  - Object with `nodeType:` (inline definition)
- Ensure inline definitions support full node type syntax
