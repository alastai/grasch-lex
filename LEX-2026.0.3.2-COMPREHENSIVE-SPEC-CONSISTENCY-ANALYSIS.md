# Part 4: Edge Type Syntax Revolution (0.3.2)

## Complete Redesign in 0.3.2

**Old Syntax (0.3.1 - DEPRECATED):**
```yaml
edgeType:
  typeLabel: KNOWS
  implies:
    propertyTypes: [...]
  direction: UNDIRECTED
  firstEndpointNodeType:
    typeLabel: Person
  secondEndpointNodeType:
    typeLabel: Person
```

**New Syntax (0.3.2 - CURRENT):**
```yaml
edgeType:
  undirected:
    between: Person
    via: KNOWS
    and: Person
  implies:
    propertyTypes: [...]
```

---

## Key Changes

### 1. Direction Integrated into Structure

**Old**: Separate `direction:` property
**New**: `directed:` or `undirected:` wrapper

### 2. Via Keyword for Edge Label

**Old**: Separate `typeLabel:` property
**New**: `via:` or `arc:` within direction block

### 3. Semantic Endpoint Names

**Directed**:
- `from:`/`to:` (primary)
- `tail:`/`head:` (synonym)
- `src:`/`dst:`/`dest:` (synonyms)

**Undirected**:
- `between:`/`and:` (primary)

### 4. Self-Loops

**New keywords**: `SAME` or `SELF` for self-referential edges

```yaml
edgeType:
  directed:
    from: Person
    via: REPORTS_TO
    to: SAME
```

# Part 6: Subtyping and Inheritance

## Two Equivalent Patterns

### Pattern 1: implies with supertypes

**Syntax:**
```yaml
nodeType:
  typeLabel: Employee
  implies:
    supertypes: Person  # or [Person]
    propertyTypes:
    - name: employeeId
      valueType: STRING
```

**Characteristics:**
- Complete redefinition
- Must list ALL properties (inherited + new)
- More verbose but explicit
- Better for documentation

---

### Pattern 2: extends with adding

**Syntax:**
```yaml
nodeType:
  typeLabel: Manager
  extends: Employee  # or [Employee]
  adding:
    propertyTypes:
    - name: department
      valueType: STRING
```

**Characteristics:**
- Incremental definition
- Only lists NEW properties
- More concise
- Better for maintenance

---

## Singleton vs Array Forms

**Both Supported:**
```yaml
# Singleton as string
supertypes: Person
extends: Employee

# Singleton as array
supertypes: [Person]
extends: [Employee]

# Multiple supertypes
supertypes: [Employee, Person]
extends: [Manager, Director]
```

**JSON Schema**: Validates both forms with oneOf.

**Examples**: Use both forms interchangeably.

**Requirements**: Does not clarify both forms are valid.

---

## Multiple Inheritance

**Supported:**
```yaml
nodeType:
  typeLabel: Manager
  implies:
    supertypes: [Employee, Person]
    propertyTypes: [...]
```

**Semantics**: Java interface mixin style.

**Examples**: Demonstrated in node-type-syntax-examples.yaml.

**Requirements**: Mentions "Java interface mixins" but lacks detail.

**Gap**: Requirements need explicit multiple inheritance specification.

---

## Edge Type Subtyping

**Supported Patterns:**

```yaml
# Base edge type
- edgeType:
    undirected:
      between: Person
      via: KNOWS
      and: Person
    implies:
      propertyTypes: [...]

# Subtype using extends
- edgeType:
    undirected:
      between: Person
      via: CLOSE_FRIEND
      and: Person
    extends: KNOWS
    adding:
      propertyTypes: [...]
```

**Subtype Rules (from API Design):**

An edge type S is a subtype of T if:
1. S's properties are subtype of T's properties (structural)
2. S's endpoints are subtypes of T's endpoints:
   - DIRECTED: source <: source AND destination <: destination
   - UNDIRECTED: endpoints match in either order
3. Direction must be compatible
4. Self-loops (SAME) require special handling

**Examples**: Extensive edge subtyping in edge-type-syntax-examples.yaml.

**Requirements**: Does NOT mention edge type subtyping.

**Critical Gap**: Requirements need edge type subtyping specification.

---

## Armstrong's Axioms

**From API Design:**

The subtype relation (<:) satisfies:
- **Reflexive**: Every type is a subtype of itself (T <: T)
- **Transitive**: If A <: B and B <: C, then A <: C

**Purpose**: Ensures consistent type hierarchy semantics.

**Requirements**: Does NOT mention Armstrong's Axioms.

**Gap**: Requirements should document formal properties of subtype relation.

---
