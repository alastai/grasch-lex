# LEX:2026.0.3.1 Implementation Guide

## Overview
This repository contains a complete implementation of the LEX:2026.0.3.1 (LDBC Extended GQL Schema) specification for property graph schema management. LEX:2026.0.3.1 is based on LEX-100r3, featuring **mandatory type labels**, **subtyping support**, **import/modularization capabilities**, and **type interpretation modes**.

## What's New in LEX:2026.0.3

### 1. Mandatory Type Labels (Breaking Change)
**Impact**: All node and edge types must have at least one label

```yaml
graphType:
  # LEX:2026.0.3 - Labels are now mandatory (minimum 1)
  nodeTypeMinimumLabels: 1  # Changed from 0 in 0.2
  edgeTypeMinimumLabels: 1  # Changed from 0 in 0.2
  
  nodeTypes:
    - nodeTypeIdentifier:
        typeLabel: "Person"  # Type name label (preferred)
      labels: ["Person"]  # At least one label required
      propertyTypes: [...]
```

**Rationale**: Aligns with GQL:2027 and simplifies type identification

### 2. Subtyping Support (New Feature)
**Impact**: Types can now declare supertypes for inheritance

```yaml
nodeTypes:
  # Base type
  - nodeTypeIdentifier:
      typeLabel: "Person"
    labels: ["Person"]
    propertyTypes:
      - name: "id"
        valueType: {name: "INTEGER"}
      - name: "name"
        valueType: {name: "STRING"}
  
  # Derived type with supertypes
  - nodeTypeIdentifier:
      typeLabel: "Employee"
    labels: ["Employee"]
    supertypes: ["Person"]  # Inherits Person's properties
    propertyTypes:
      - name: "employeeId"
        valueType: {name: "INTEGER"}
```

**Behavior**: Supertypes pull in labels and property types (Java interface mixin style)

### 3. Import/Modularization via $ref (New Feature)
**Impact**: Schemas can be modularized and imported

```yaml
graphType:
  nodeTypes:
    $ref: 'common-node-types.yaml'  # Import from external file
  
  edgeTypes:
    - edgeTypeIdentifier:
        typeLabel: "KNOWS"
      labels: ["KNOWS"]
      propertyTypes:
        $ref: 'common-edge-properties.yaml'  # Import properties
      direction: "DIRECTED"
      firstEndpointNodeTypeIdentifier:
        typeLabel: "Person"
      secondEndpointNodeTypeIdentifier:
        typeLabel: "Person"
```

**Use Case**: Distributed/partitioned schemas, reusable type definitions

### 4. Type Interpretation Modes (New Feature)
**Impact**: Control how types are validated

```yaml
graphType:
  typeInterpretation: "exactlyOfThisType"  # Default
  # Options:
  # - "exactlyOfThisType": Exact match required (default)
  # - "anySubtypeOf": Covariant - at least these attributes
  # - "anyProperSubtypeOf": Proper subtype required
  
  nodeTypes: [...]
```

**Use Case**: Flexible validation for open vs. closed type systems

### 5. Extension Interpretation (New Feature)
**Impact**: Control whether types can be extended

```yaml
nodeTypes:
  - nodeTypeIdentifier:
      typeLabel: "Person"
    labels: ["Person"]
    extensionInterpretation:
      open: true  # Allow undefined subtypes
    propertyTypes:
      - name: "id"
        valueType: {name: "INTEGER"}
    # Property types can have separate extension interpretation
    extensionInterpretation:
      closed: true  # Only defined property types allowed
```

**Default**: `closed: true` (GQL:2027 setting)

### 6. File References in Catalogs (New Feature)
**Impact**: Catalog entries can reference external files

```yaml
catalog:
  IRI: "https://ldbcouncil.org/schemas/"
  directories:
    - name: "benchmarks"
      graphSchemas:
        - name: "snb"
          file: $ref('schemas/snb-schema.yaml')  # File reference
```

**Use Case**: Separate IRI from actual file location

## Migration from 0.2.1 to 0.3.1

### Breaking Changes

#### 1. Mandatory Labels
**Before (0.2.1)**:
```yaml
graphType:
  nodeTypeMinimumLabels: 0  # Labels optional
  nodeTypes:
    - nodeTypeIdentifier:
        nodeTypeIndex: 0
      labels: []  # Empty labels allowed
      propertyTypes: [...]
```

**After (0.3.1)**:
```yaml
graphType:
  nodeTypeMinimumLabels: 1  # At least one label required
  nodeTypes:
    - nodeTypeIdentifier:
        typeLabel: "MyType"  # Use type name label
      labels: ["MyType"]  # At least one label required
      propertyTypes: [...]
```

### New Optional Features

#### 2. Subtyping (Optional)
```yaml
nodeTypes:
  - nodeTypeIdentifier:
      typeLabel: "Employee"
    labels: ["Employee"]
    supertypes: ["Person"]  # NEW in 0.3
    propertyTypes: [...]
```

#### 3. Imports (Optional)
```yaml
graphType:
  nodeTypes:
    $ref: 'common-types.yaml'  # NEW in 0.3
```

#### 4. Type Interpretation (Optional)
```yaml
graphType:
  typeInterpretation: "anySubtypeOf"  # NEW in 0.3
  nodeTypes: [...]
```

## Key Improvements in 0.3.1

1. **Mandatory Labels**: All types must have at least one label (breaking change)
2. **Subtyping Support**: Types can declare supertypes for inheritance
3. **Import/Modularization**: Schemas can be split across files using $ref
4. **Type Interpretation**: Control validation behavior (exact, subtype, proper subtype)
5. **Extension Interpretation**: Control whether types can be extended
6. **File References**: Catalog entries can reference external files
7. **Simplified Examples**: Focus on typeLabel identification (preferred method)

## Backward Compatibility

### Compatible with 0.2.1
- Schemas with labels will validate against 0.3.1
- New features are optional and backward compatible
- Default behaviors match 0.2.1 where applicable

### Incompatible with 0.2.1
- Schemas without labels will fail validation
- Minimum label constraints changed from 0 to 1
